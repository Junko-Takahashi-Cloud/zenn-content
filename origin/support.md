# Support ― 完成したスポーツボウリング場システムを支える仕組み

スポーツボウリング場構想では、予約システムから始まり、店舗運営、会員管理、メンテナンス、投球データ分析、フロントエンドまで開発を進めてきました。

最後に整理したいのが、**このシステムが実際の店舗運営をどのように支えるのか**という「Support」です。

Supportは新しい機能を追加するための章ではありません。これまで作ってきた機能を、利用者・スタッフ・インストラクター・設備・データという複数の視点から捉え直し、ひとつの店舗運営システムとして整理するためのものです。

## 1. 利用者を支える

利用者側では、単に「予約できる」だけではありません。予約から来店、利用、継続利用までの流れを支えます。

- 予約管理
- 来店受付・チェックイン
- レーン利用
- 会員情報
- マイボール・マイシューズなどのギア情報
- 投球・ゲーム記録
- スコア分析
- 最近のゲーム履歴
- ギア別のパフォーマンス確認
- 教室修了・達成バッジ/称号(AchievementBadge)

投球データは、フレームや残ピンの情報をもとに、ストライク・スペア・タップ・スプリット・オープンなどを分析できるようにしました。会員にとっては、単なる「スコアを見る場所」ではなく、自分のボウリングを振り返るための情報になります。

また、教室を修了した会員には達成バッジや称号が付与される仕組みも用意しています。上達の過程そのものが、記録として残っていく形です。

無断キャンセル・当日キャンセルについては、キャンセル料のような金銭的なペナルティは設けていません。会員のメールアドレス単位で記録し、無断キャンセルと当日キャンセルを同じ重みでカウントします。2ヶ月のローリング期間内に3回溜まった時点で、次回予約が制限される仕組みです。期間が過ぎれば古い記録は対象から外れるため、恒久的な制限ではなく、直近の利用状況に応じて可変する制御になっています。

## 2. スタッフを支える

店舗側には、日々発生するさまざまな業務があります。今回のシステムでは、スタッフ向けのフロントエンドも実装しました。

- スタッフ登録
- 出退勤・タイムカード
- 来店受付
- レーン状態確認
- コーチのシフト管理
- 教室の出席管理
- 支払い確認・決済登録

レーンは「利用可能」「利用中」「故障中」「メンテナンス中」といった状態を管理できます。また、決済では料金確認から支払い登録までを扱い、入力値や存在しないIDなどもチェックするようにしました。

## 3. インストラクターを支える

スポーツボウリング場では、設備だけでなく人による指導も重要です。そのため、コーチシフト・教室管理・出席管理・会員の投球履歴などを店舗運営の中に含めています。

システムが指導そのものを代替するのではなく、インストラクターが利用者を見るための情報を整理する、という位置付けです。

## 4. レーンと設備を支える

店舗運営では、レーンが使える状態を維持することが欠かせません。店舗側メンテナンス管理では、貸出用品だけでなく、レーン設備のメンテナンスも扱います。

メンテナンス記録には、対象・メンテナンス種別・状態・修理方法・業者・実施者・費用・実施日・メモなどを記録します。

貸出用品については、廃棄した場合も物理的に履歴を消すのではなく、状態を「廃棄」とする論理削除にしています。これにより、過去の整備・廃棄履歴を残せます。

## 5. システム同士を連携する

今回の開発では、それぞれの機能を独立したものとして終わらせず、システム間の連携も実装しました。

例えば、第三弾の店舗管理側でレーンが「故障中」になると、メンテナンス管理側へ自動的に登録できます。また、会員側からメンテナンスを依頼すると、メンテナンス管理側で完了した情報を会員のギア履歴へ反映できます。

つまり、**店舗側 → メンテナンス側**だけではなく、**会員側 → メンテナンス側 → 会員側**という双方向の流れも作っています。

## 6. データを支える

第五弾では、これまで蓄積してきたデータを分析するところまで進めました。

会員向け画面では、スコア・ストライク・スペア・オープン・フレーム分析・ギア別パフォーマンス・最近のゲームなどを確認できます。スタッフ向け画面では、店舗全体の状況・レーン別の状況・コンディション別の状況を確認できます。

さらに、実機から取得したデータをCSVで取り込む仕組みも実装しました。1投を1行として扱うCSVから、レーン番号や時刻などを使って該当するゲーム・会員を特定し、投球データとして登録します。実機そのものを用意できなくても、実際の機器から来るデータを想定した入口まで作ることができました。

## 7. フロントエンドまでつなげる

このプロジェクトは長い間、FastAPIを中心としたバックエンド開発が中心でした。第三弾と第五弾では、React + Viteによるフロントエンドを追加しています。

第三弾では店舗スタッフが操作する7画面を実装し、第五弾では会員・スタッフ向けの分析画面を実装しました。これによって、APIだけではなく、**「実際に人が触るシステム」**として全体像を確認できるようになりました。

なお、第一弾・第二弾はもともとStreamlitでフロントエンドを持っており、第四弾はバックエンド完結のプロジェクトです。全プロジェクトを一つの技術で統一するのではなく、プロジェクトごとの性質と目的に応じて技術を選び分けています。

## 8. 技術構成の広がり

このプロジェクト全体が単一の技術スタックに移行したわけではありません。プロジェクトごとに、目的に応じて技術を選び分けてきました。

- 第一弾・第二弾:FastAPI + SQLAlchemy + SQLite + Streamlit(最初から一貫)
- 第三弾・第四弾:FastAPI + SQLAlchemy + SQLite(バックエンド中心)。第三弾は後にReact + Viteのフロントエンドを追加
- 第五弾:第三弾・第四弾と同じくFastAPI + SQLiteのバックエンドに、React + Vite + Rechartsのフロントエンドを追加
- 拡張①(メンテナンス管理):新しい技術スタックに挑戦する実験場として、あえて別リポジトリ・別DBで構築。FastAPI + PostgreSQL + Docker Compose + AWS EC2という、他プロジェクトとは異なる構成を採用

PostgreSQL・Docker・AWSは拡張①だけ、Reactは第三弾・第五弾だけの挑戦です。「全部を一気に新しくする」のではなく、プロジェクトごとに挑戦する技術を絞り込んだことが、結果的にどの技術も中途半端にせず終わらせられた理由だと感じています。

加えて、APIキー認証、CORS、入力バリデーション、エラーメッセージの共通化など、実運用を意識した部分も各プロジェクトで追加しています。

## 9. Supportの考え方

このプロジェクトで考えてきたSupportは、「問い合わせ対応」だけを意味していません。

利用者を支える。スタッフを支える。インストラクターを支える。設備を支える。データを支える。そして、それぞれをつなぐ。

その結果として、スタッフが本来人に向き合うべき仕事へ時間を使えるようにする。システムが人の仕事をすべて置き換えるのではなく、**人が人にしかできない仕事へ集中できる環境を作ること**が、この構想におけるSupportの役割です。

## 10. ここまで作ってきたもの

振り返ると、このプロジェクトは「ボウリング場の予約システムを作る」ことから始まりました。

そこから、**予約 → 店舗運営 → 会員管理 → ギア管理 → メンテナンス → 投球データ → 分析 → フロントエンド → システム間連携**へと広がっていきました。

最初からすべてを作ろうとしたわけではありません。ひとつ作り、実際に使う場面を考え、足りないものを見つけ、次の機能へ進む。その繰り返しで、ひとつのスポーツボウリング場を支えるシステムへ形を変えていきました。

## おわりに

スポーツボウリング場構想は、ここでひと区切りです。

「こんなボウリング場があったらいい」という構想から始まり、AIと対話しながら要件を考え、設計し、実装し、データベースを作り、APIを作り、拡張①ではAWSへのデプロイまで経験し、第三弾・第五弾ではフロントエンドまでつなぎました。

そして最後に残ったのが、この **Support** でした。

Supportは新しい機能ではありません。これまで作ってきたものを、実際の店舗と利用者の視点から見直したときに見えてくる、システム全体の役割そのものです。

**スポーツボウリングを楽しむ人を支え、
そこで働く人を支え、
設備を支え、
蓄積されたデータを支える。**

それが、このプロジェクトで考えた「Support」です。

🎳 スポーツボウリング場構想は、ここで完全終了です。
