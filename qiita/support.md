## 完成したシステム、あらためて数えてみる

スポーツボウリング場構想では、予約機能から始めて、店舗運営、会員・ギア管理、メンテナンス、投球データ分析、Reactフロントエンドまで段階的に実装してきました。

最後に、完成したシステム全体を「Support」という観点から整理します。

- 予約・来店受付
- 店舗スタッフ管理
- レーン状態管理
- コーチ・教室管理
- 決済
- 会員・ギア管理
- 貸出用品管理
- メンテナンス管理
- 投球データ登録・スコア分析
- 会員向け画面・スタッフ向け画面
- 実機CSVデータ取込
- システム間API連携

数えてみると、「予約アプリ」の範囲をだいぶ超えていました。

## 技術は、全部を一気に新しくしなかった

これだけプロジェクトが増えると、「せっかくだから全部最新技術に統一したい」という気持ちも出てきます。でも今回は、あえてそれをしませんでした。

- 第一弾・第二弾:FastAPI + SQLite + Streamlit(最初からずっとこのまま)
- 第三弾・第四弾:FastAPI + SQLite(バックエンド中心)。第三弾だけ後からReact + Viteを追加
- 第五弾:FastAPI + SQLiteのバックエンドに、React + Vite + Rechartsのフロントエンドを追加
- 拡張①:新しい技術の実験場として別リポジトリ・別DBに切り出し、FastAPI + PostgreSQL + Docker Compose + AWS EC2に挑戦

PostgreSQL・Docker・AWSに挑戦したのは拡張①だけ、Reactに挑戦したのは第三弾・第五弾だけです。全部を一気に新しくしようとすると、結局どれも中途半端になりがちだと思っていたので、挑戦する技術をプロジェクトごとに絞り込んだのは、個人的には良い判断だったと感じています。

## 利用者側のSupport

会員側では、予約だけでなく、利用後の情報活用までを対象にしました。

スコア分析では、投球データからストライク、スペア、タップ、スプリット、オープンなどを分類します。会員画面では、スコアやフレーム分析、ギア別パフォーマンス、最近のゲームなどを確認できます。教室を修了した会員には達成バッジ・称号も付与される仕組みです。

### 無断キャンセル・当日キャンセルの扱い

キャンセル料を取る設計にはしていません。金銭的なペナルティではなく、予約運用上の制御として扱っています。

記録は会員のメールアドレス単位です。無断キャンセル(no-show)と当日キャンセル(late-cancel)は、同じ重みで1件としてカウントします。2ヶ月のローリング期間内に3回溜まった時点で、次回予約が制限されます。期間が経てば古い記録は外れていくので、一度制限されたらずっと、というわけではありません。

## 店舗側のSupport

第三弾では、店舗スタッフが扱う業務をAPIとReactフロントエンドの両方から実装しました。完成した画面は次の7つです。

1. スタッフ登録
2. スタッフ出退勤・タイムカード
3. 来店受付・チェックイン
4. レーン状態管理
5. コーチシフト管理
6. 教室出席管理
7. 支払い確認

レーン状態は、利用可能・利用中・故障中・メンテナンス中などを管理します。入力値の必須チェックや、存在しないIDに対する404処理、時刻の前後関係のチェック、FastAPI/Pydanticのエラーを日本語表示へ変換する共通処理も実装しました。

## メンテナンスSupport

拡張①では、店舗側のメンテナンス管理を実装しました。対象はレーン設備・貸出シューズ・貸出ボールなどの用品です。

メンテナンス記録には、対象、種別、状態、修理方法、業者、実施者、費用、実施日、メモなどを記録します。用品を廃棄する場合は物理削除せず、状態を「廃棄」とする論理削除にしています。これにより、過去の管理履歴を保持できます。

## システム間連携

第三弾でレーンを「故障中」に変更すると、メンテナンス管理側へ自動登録します。また、会員側からのメンテナンス依頼をメンテナンス管理へ送り、完了情報を会員のギア履歴へ戻す双方向連携も実装しています。拡張①が落ちていても第三弾・第四弾の処理は止めない、という例外設計も入れました。

## 投球データと分析

第五弾では、投球データを使った分析機能を実装しました。バックエンドでは、フレームや残ピン情報をビットマスクで処理し、投球結果を分類します。会員別・ギア別・レーン別・コンディション別の分析へ広げました。

実機から取得するデータについては、1投1行のCSVを受け付けるAPIを用意しました。レーン番号とタイムスタンプから対象セッションやプレイヤーを逆引きし、投球データとして登録します。

## フロントエンド

バックエンド中心だったプロジェクトに、第三弾・第五弾ではReact + Viteを導入しました。第三弾では店舗スタッフ向け7画面、第五弾では会員・スタッフ向け分析画面を実装しています。グラフ表示にはRechartsを利用し、APIと接続した実データ表示まで行いました。

これによって「APIが動く」だけではなく、「人が操作する」ところまで確認できる構成になりました。

## Supportとは何だったのか

このプロジェクトでのSupportは、FAQや問い合わせ窓口だけを指すものではありません。

利用者を支える。スタッフを支える。インストラクターを支える。設備を支える。データを支える。そして、それらをシステム間でつなぐ。

システムによって人を置き換えるのではなく、人が本来向き合うべき仕事に集中できるようにする。それが、この構想におけるSupportです。

## 最後に

予約システムとして始めたものが、店舗運営、会員管理、メンテナンス、データ分析、フロントエンド、システム間連携まで広がりました。構想 → 要件整理 → 実装 → 連携 → UI → データ活用という流れを、一つの個人開発として経験できたことが、このプロジェクトで得た大きなものです。

これで、スポーツボウリング場構想は完全終了です。
