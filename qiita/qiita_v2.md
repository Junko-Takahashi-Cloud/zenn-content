# 「スポーツボウリング場」構想をシステムとして育てる ― ポートフォリオ第二弾

## 実装し終えてから「これは違う」と気づいた機能がある

第二弾の開発中、一度作り終えた機能の設計方針を、丸ごと見直すことになりました。原因は、要件を詰め切らないまま実装に入ったからです。この記事では、その経緯と、今回初めてAI(Claude)を唯一の壁打ち相手として設計から実装まで進めた過程を書きます。

## 第一弾からの続き

事務職20年からVBA・AIエンジニアを目指す過程で作った「レーン予約システム」の第一弾は、FastAPI + SQLite + Streamlitで、個人予約(一般利用・競技者練習)の基本フローが動くところまで完成させました。第一弾は複数のAI(ChatGPT、Copilot、Gemini)にレビューしてもらいながら進めましたが、今回の第二弾は**Claude一人との対話だけ**で設計・実装・デバッグ・Git運用まで完結させています。

今回追加したのは以下です。

- 初心者教室(全5回コース)の自動生成・個人申込・団体申込
- 「一般利用」を教室修了者限定にする資格チェック
- クラウドファンディング特典(レーン貸し切り)の予約機能

## 設計で一番苦労した点:「教室コースの自動生成」

コースは「毎週土曜10:00〜、全5回」のように、開始日と曜日だけ決めれば、残り4回分の日付が自動的に決まる構造にしたいと考えました。

```python
session_dates = [payload.first_date + timedelta(weeks=i) for i in range(payload.session_count)]
```

5回分の日付を計算したあと、**そのうち1回でもレーンの予約が重複していたら、コース全体を作らない**というトランザクション的な扱いにしています。これは、既存の個人予約(V1)で使っていた重複チェックロジック(`_has_overlap`)をそのまま再利用することで実現しました。V1のロジックには一切手を加えず、拡張だけで対応できたのは、最初の設計(レーンセット×日時で重複を判定する、というシンプルな仕組み)がしっかりしていたおかげだと思います。

## 実装したのに、途中で「これは違う」と気づいた機能

最初、「団体予約」という汎用的な予約種別(`reservation_type='group'`)を作って、レーンをまとめて確保できる機能を実装しました。バックエンド・フロントとも一通り動くところまで作ったのですが、実装し終えてから「あれ、これは自分が最初に考えていた構想と違う」と気づきました。

自分の構想では、「団体」は教室への参加方法のバリエーション(職場のグループで教室に参加する)であって、独立した予約種別ではなかったのです。一方で、実装した汎用的な「団体予約」は、クラウドファンディングの特典(レーン貸し切り)としてなら意味がある、と気づき、位置づけを変えて活かすことにしました。

- `POST /reservations/group` → クラウドファンディング特典(レーン貸し切り)専用に位置づけ直し
- 教室への団体申込は、`class_courses`配下に新しく`enroll-group`エンドポイントとして追加

作ったコードを無駄にせず、意味づけを変えて活かせたのは、実装してから設計の矛盾に気づけたからこそだと思います。

## 「一般利用」の資格チェック

構想では、この施設は「スポーツとしてボウリングを楽しむ場所」であり、誰でも使える一般客向け施設ではありません。教室でマナーを学んだ人だけが使える「一般利用」枠、という位置づけです。

これをシステム上で表現するために、新しいフラグ(`is_certified`のようなカラム)を追加するのではなく、既存の教室申込データから動的に判定する方式にしました。

```python
def _is_certified(db: Session, user_id: int) -> bool:
    enrollments = (
        db.query(ClassEnrollment)
        .join(ClassCourse, ClassEnrollment.course_id == ClassCourse.course_id)
        .filter(ClassEnrollment.user_id == user_id, ClassEnrollment.status == "enrolled")
        .all()
    )
    today = date.today()
    for e in enrollments:
        last_session_date = e.course.first_date + timedelta(weeks=e.course.session_count - 1)
        if last_session_date <= today:
            return True
    return False
```

「修了フラグを管理者が手動で立てる」運用を避け、データから自動的に導ける設計にすることで、余分な管理コストを増やさずに済みました。

## Gitでの運用

今回は`v2-development`ブランチを切って作業し、Pull Requestを経由して`main`にマージする、という流れをきちんと踏みました。V1(`main`)は無傷のまま残り、コミット履歴とPRの説明文で「何を、なぜ追加したか」が追える状態になっています。

## 単一のAIと壁打ちする、という選択

第一弾は複数のAIの意見を突き合わせて設計を固める進め方でしたが、今回は逆に、Claude一人に絞って最初から最後まで対話を続けました。結果として、コードのスタイルや設計判断の一貫性(命名規則、エラーハンドリングの方針、コメントの書き方)が保ちやすかったと感じています。複数AIのレビューは視点の多様性が強みですが、単一AIとの継続対話は「積み上げの一貫性」が強みだと、両方をやってみて実感しました。
