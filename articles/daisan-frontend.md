## エラーメッセージの整形を共通化する

バックエンドのバリデーションエラーは、Pydanticの仕様上、単一エラーだと文字列、複数エラーだと配列で返ってくることがあります。これを画面ごとに個別対応していると、表示ロジックが分散して保守性が落ちます。

そこで `src/utils/errorMessage.js` に `formatErrorMessage` という共通関数を用意し、レスポンスの形式に関わらず1つの読みやすい文章に変換する設計にしました。7画面すべてがこの関数を経由してエラーを表示するため、今後画面を追加してもロジックを再利用できます。

```js
// src/utils/errorMessage.js のイメージ
export function formatErrorMessage(detail) {
  if (Array.isArray(detail)) {
    return detail.map((e) => e.msg ?? String(e)).join(" / ");
  }
  return String(detail);
}
```

## 入力チェックは「フロント」と「バックエンド」の両輪で

決済確認画面で見つかった問題は、レーンID・チェックインID・金額が未入力のまま送信できてしまう点でした。未入力の項目は0やnullとして送信され、存在しないデータに対する0円決済が登録される可能性がありました。

対応は2段構えにしています。

1. フロント側:必須項目が空欄なら送信自体をブロック
2. バックエンド側:存在しないレーンID・チェックインIDが渡された場合は404を返す

フロント側だけでは直接APIを叩かれた場合に無力で、バックエンド側だけではユーザー体験が悪化します。両方を揃えることで、初めて実用に耐える形になりました。
