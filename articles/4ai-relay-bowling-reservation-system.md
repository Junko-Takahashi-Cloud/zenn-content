AIと協働してシステムを作る──この言葉はキャッチーですが、実際の開発はもっと泥臭く、もっと人間的で、もっと面白いものでした。今回のボウリング場予約システム開発は、ChatGPT・Copilot・Gemini・Claudeの4AIがリレー形式で担当しながら、要件定義→設計→DB設計レビュー→実装・デバッグという流れを走り抜けたプロジェクトです。

Zenn向けの記事として、Qiita版よりも「技術的な判断根拠」「設計の深さ」「コード例」を厚くしながら、4AIそれぞれの視点をそのまま残して再構成しています。

---

## 第1走者：ChatGPT ― 要件定義は「育てるもの」だった

最初の工程は要件定義でした。予約システムは一見シンプルですが、実際には多くの判断が必要です。

- 同一利用者の時間帯重複予約は許可するか
- レーンセット（アメリカン方式）をどう扱うか
- 認証は簡易認証か、JWTか
- キャンセル権限は誰に与えるか

こうした仕様は、後工程の設計・実装に大きく影響します。

ChatGPTは、要件定義書（Ver.1 → Ver.2 → Ver.2.1）を段階的に育てながら、曖昧な仕様をひとつずつ言語化していきました。特に、予約の重複判定（E001/E002/E003）や、JWT認証の採用、キャンセル権限の扱いなどは、後工程の設計に直結する重要な判断でした。

## 第2走者：Copilot ― 設計は「骨格を描く仕事」であり、技術的判断の連続だった

要件定義が固まった段階で、私（Copilot）がバトンを受け取りました。担当は「設計統括」。複数AIのアウトプットを統合し、実際に動くシステムへ落とし込む交通整理役です。

### なぜ4テーブル構成なのか（技術的判断）

予約管理の中心となるのは以下の4テーブルです。

```
Users
LaneSets
Lanes
Reservations
```

この構成にした理由は、**正規化・拡張性・整合性の3点を満たすため**です。

**Users**
認証情報（email/password）と権限（一般ユーザー/管理者）を管理します。

**LaneSets**
ボウリング場では「2レーン1組（アメリカン方式）」が一般的です。レーンセットを独立させることで、予約単位を自然に表現できます。

**Lanes**
物理レーンの稼働状態（通常/メンテナンス）を管理します。これを独立させることで、片方のレーンだけがメンテ中の場合でも、レーンセット全体の予約を自動的にブロックできます。

**Reservations**
誰が、どのレーンセットを、いつ予約したかを記録します。

この構造は、以下のようなER図で表現できます。

```
Users (1) --- (N) Reservations (N) --- (1) LaneSets (1) --- (N) Lanes
```

### API設計の判断根拠

FastAPIを採用した理由は以下の通りです。

- Pydanticによる型安全なスキーマ定義
- 非同期処理が標準で使える
- JWT認証との相性が良い
- Claudeが実装しやすい構成である

APIは以下のように整理しました。

```
POST /auth/register
POST /auth/login
GET  /lanesets
POST /reservations
DELETE /reservations/{id}
GET  /admin/reservations
POST /admin/lanes/{id}/maintenance
```

### 技術選定（FastAPI＋SQLite＋Streamlit）の理由

**FastAPI**
軽量でMVPに最適。型安全でClaudeが実装しやすい。

**SQLite**
ローカル開発に最適。排他制御は簡易的にLockで対応。

**Streamlit**
UIを最短で構築できる。純子さんがローカルで動作確認しやすい。

### ファイル構成案（VS Code前提）

```
backend/
  app/
    main.py
    database.py
    models/
    schemas/
    routers/
frontend/
  app.py
```

この構成は、後工程のClaudeが迷わず実装できるように設計したものです。

### 実装は担当しなかった（正直な事実）

当初の役割表では「Copilot＝実装統括」でしたが、実際に担当したのは**設計フェーズまで**でした。

- ER図
- API設計
- 技術選定
- ファイル構成案

これらの“骨格づくり”を担い、実装はClaudeへ託しました。

設計はシステムの未来を決める工程です。私はその部分を責任を持って担当し、次の走者へバトンを渡しました。

## 第3走者：Gemini ― DB設計レビューは、理想と現実の「翻訳作業」だった

Geminiは、Copilotが描いた設計をもとに、DB設計のレビューを担当しました。

### Geminiが提示した4テーブル構成の強化ポイント

- 個別レーン管理（Lanes）を独立させる
- レーンセットと物理レーンの整合性を担保する
- SQLiteの外部キー制約を有効化する
- タイムスタンプ（作成日時・キャンセル日時）を追加する

### 懸念点として提示したポイント

- ダブルブッキング防止はアプリ側で実装が必要
- レーンセットの整合性ロジック
- 外部キー制約の有効化
- 監査ログの不足

### 協働開発ならではの「ゆらぎ」

Geminiが独立させた`Lanes`テーブルが、Copilotの実装寄り設計ではカンマ区切り文字列に後退していた──この“ゆらぎ”をClaudeが検出し、要件定義の改訂につながりました。

複数AIが並行して設計すると、こうしたグラデーションが自然に発生します。これは失敗ではなく、協働開発のリアルな学びでした。

---

## 第4走者：Claude ― レビューのつもりが、実装からデバッグまで担当することになった

Claudeは当初「設計レビュー・品質チェック」の担当でしたが、体制の見直しにより、最終的に実装まで担当することになりました。

### 実装で遭遇したトラブル

- bcryptのバージョン競合
- StreamlitのMagic機能による`set_page_config()`エラー
- フォルダ構成の崩壊
- バックエンド起動忘れによる接続エラー
- Windows Smart App Controlによるzipブロック
- SQLiteの永続化による誤解

これらをひとつずつ切り分けながら、動くMVPを完成させました。
