## この記事でわかること

- 予約から店舗運営・会員管理・メンテナンス・データ分析・フロントエンドまで、最終的にどんなシステム構成になったか
- プロジェクトごとに技術スタックを使い分けた理由(全体を一つの技術に統一しなかった判断)
- システム間連携(第三弾⇄拡張①、第四弾⇄拡張①)の設計
- 無断キャンセル制御の実装ルール

## システム全体像

最終的なシステムは、単純な予約アプリではありません。

- 予約・来店受付
- 店舗スタッフ管理
- レーン状態管理
- コーチ・教室管理
- 決済
- 会員・ギア管理
- 貸出用品管理
- メンテナンス管理
- 投球データ登録・スコア分析
- 会員向け画面・スタッフ向け画面
- 実機CSVデータ取込
- システム間API連携

までを扱います。

## 技術構成:あえて統一しなかった理由

このプロジェクト全体が単一のスタックへ移行したわけではありません。プロジェクトごとに、目的に応じて技術を選び分けています。

| プロジェクト | バックエンド | フロントエンド | 備考 |
|---|---|---|---|
| 第一弾・第二弾 | FastAPI + SQLAlchemy + SQLite | Streamlit | 最初から一貫した構成 |
| 第三弾・第四弾 | FastAPI + SQLAlchemy + SQLite | 第三弾のみReact + Vite | 第四弾はバックエンド完結 |
| 第五弾 | FastAPI + SQLAlchemy + SQLite | React + Vite + Recharts | データ可視化を重視しReactを採用 |
| 拡張① | FastAPI + PostgreSQL | ― | Docker Compose + AWS EC2への実験的挑戦 |

PostgreSQL・Docker・AWSは拡張①だけ、Reactは第三弾・第五弾だけの挑戦です。全プロジェクトを同時に新しい技術へ移行するのではなく、あえて1プロジェクトずつ挑戦範囲を絞ったことが、結果的にどの技術も中途半端にせず実務レベルまで理解を深められた理由だと考えています。

加えて、APIキー認証、CORS、入力バリデーション、エラーメッセージの共通化(FastAPI/Pydanticのバリデーションエラーを日本語の1文に整形する処理)など、実運用を意識した部分も各プロジェクトで追加しています。

## 利用者側のSupport

会員側では、予約だけでなく利用後の情報活用までを対象にしています。

投球データはフレームや残ピン情報をビットマスクで処理し、ストライク・スペア・タップ・スプリット・オープンなどに分類します。会員画面ではスコア・フレーム分析・ギア別パフォーマンス・最近のゲームなどを確認でき、教室を修了した会員には達成バッジ・称号(AchievementBadge)が付与されます。

### 無断キャンセル・当日キャンセルの制御

キャンセル料のような金銭的なペナルティは設けていません。会員のメールアドレス単位で記録し、無断キャンセル(no-show)と当日キャンセル(late-cancel)を同じ重みで1件としてカウントします。2ヶ月のローリング期間内に3回溜まった時点で、次回予約が制限される仕組みです。期間経過で古い記録は対象から外れるため、恒久的な制限ではなく直近の利用状況に応じて可変する制御になっています。

## 店舗側のSupport

第三弾では、店舗スタッフが扱う業務をAPIとReactフロントエンドの両方から実装しました。

1. スタッフ登録
2. スタッフ出退勤・タイムカード
3. 来店受付・チェックイン
4. レーン状態管理(利用可能/利用中/故障中/メンテナンス中)
5. コーチシフト管理
6. 教室出席管理
7. 支払い確認

入力値の必須チェック、存在しないIDに対する404処理、時刻の前後関係のチェック、FastAPI/Pydanticのエラーを日本語表示へ変換する共通処理も実装しています。

## メンテナンスSupport(拡張①)

対象はレーン設備・貸出シューズ・貸出ボールなどの用品です。メンテナンス記録には対象・種別・状態・修理方法・業者・実施者・費用・実施日・メモなどを記録します。

用品を廃棄する場合は物理削除せず、状態を「廃棄」とする論理削除にしています。これにより過去の管理履歴を保持できます。

## システム間連携

第三弾でレーンを「故障中」に変更すると、メンテナンス管理側(拡張①)へ自動登録します(APIキー認証付きPOST)。また、会員側(第四弾)からのメンテナンス依頼をメンテナンス管理へ送り、完了情報を会員のギア履歴へ戻す双方向連携も実装しています。

拡張①側が落ちていても第三弾・第四弾の処理は止めない、という例外設計も意識しています。

## データとフロントエンド

第五弾では、蓄積してきたデータを分析するところまで実装しました。会員別・ギア別・レーン別・コンディション別の分析に加え、実機から取得するデータについては1投1行のCSVを受け付けるAPIを用意しています。レーン番号とタイムスタンプから対象セッション・プレイヤーを逆引きし、投球データとして登録します。

第三弾・第五弾では、最後の段階でReact + Viteによるフロントエンドを実装しました。グラフ表示にはRechartsを利用し、APIと接続した実データ表示まで確認済みです。これによって「APIが動く」だけではなく、「人が操作する」ところまで確認できる構成になりました。

## Supportとは何だったのか

このプロジェクトでのSupportは、FAQや問い合わせ窓口だけを指すものではありません。利用者を支える。スタッフを支える。インストラクターを支える。設備を支える。データを支える。そして、それらをシステム間でつなぐ。

システムによって人を置き換えるのではなく、人が本来向き合うべき仕事に集中できるようにする。それが、この構想におけるSupportです。

## 最後に

予約システムとして始めたものが、店舗運営、会員管理、メンテナンス、データ分析、フロントエンド、システム間連携まで広がりました。プロジェクトごとに挑戦する技術を絞り込みながら進めたことが、結果的に無理のない完走につながったと感じています。

これで、スポーツボウリング場構想は完全終了です。
